# Macro Adoption and API Evolution: Theory

[Concept overview](README.md) · [Interview questions](interview.md)

## Mental Model

A macro is build infrastructure and API generator, not a local syntax shortcut.

## How It Works

Consumers compile against expanded declarations. Renaming a generated member, adding
an overload, or changing conformance can break them without changing the macro call.
Persisted or wire behavior generated by a macro requires separate schema versioning.

For example, this invocation looks unchanged across releases:

```swift
@MemberwiseInit
struct Account {
    let id: String
    let name: String
}

let account = Account(id: "42", name: "Mina")
```

If a later macro expansion renames an initializer label, changes its access level,
or adds a conflicting overload, the call can stop compiling even though the
`@MemberwiseInit` line did not change. Expansion snapshots and compiled consumer
fixtures must therefore be versioned with the macro package.

Adoption should establish supported toolchains, dependency ownership, build cache
behavior, security review, documentation, expansion inspection, and rollback.

### Rules That Must Stay True

- Generated API has explicit versioning rules.
- Builds remain reproducible and diagnosable.
- Persisted formats are not coupled accidentally to expansion details.
- Consumers can migrate incrementally.
- One team owns compatibility and incident response.

## Engineering Judgment

Adopt when repetitive compile-time structure is large, stable, error-prone by hand,
and centrally ownable. Reject when the expansion is tiny, changes frequently, or would
hide business behavior. Require measurable build and maintenance budgets.
